# Liveness rows: FuzzStream

FuzzStream (`internal/fuzzkit/stream_test.go`) is target T0 of
[the nightly fuzzing plan](../specs/nightly-fuzzing-plan.md). These rows
answer §10's question for it: can this harness find a defect at all, and
which detector reports it. They are run by

    just fuzz-liveness FuzzStream

which executes `.github/scripts/fuzz-liveness/FuzzStream.rows` through
`driver.sh` beside it. Each row plants one `sed` mutation in a
`git archive HEAD` extract under `mktemp -d`, never in a checkout.

## The run

Measured 2026-10-27 at `3cc76ada` (branch `feat/gqlc-jjot2.2-fuzzkit`),
go1.27.3, 24 CPUs, default `-parallel`, budget `LIVENESS_BUDGET=5m`. Every
row and control started from an empty grown corpus (`GQLC_FUZZ_CACHEDIR` set
per row), so the times are from the committed seeds alone. Wall time includes
`just fuzz`'s own `fuzz-list` discovery, about 3 s warm.

The md5 columns pin **movement, not identity** (see
[README](README.md)): they are the first 8 hex digits of the file before and
after the `sed`, and the diffs below are the bytes.

What each row means:

- **R2 is the row that says the fuzzer, not the corpus, finds things.** Before
  fuzzing, the driver ran the mutant's committed seeds (`go test -run
  '^FuzzStream$'`) and they were green, so no seed meets `0x3c` followed by
  `0xa7`; none of the five seeds carries `0xa7` at all. The engine found an
  input that does inside the budget and wrote it to
  `testdata/fuzz/FuzzStream/`. The 4 s is mostly discovery; the plan's warning
  about an R2 that kills in under a second is answered by that seed check,
  which is part of the row rather than a later re-check.
- **R3 answers §5's open question with one measurement:** a call that returns
  late is reported by `fuzzkit.Guard`, as `slow input: the call took 20.018s,
  over the 2s limit` (20 s because both of FuzzStream's streams read the
  trigger, so it slept twice). The engine did **not** report it as a hung
  worker first, and nothing reported a test timeout. The 88 s is the find plus
  the engine's minimisation of the crasher, each minimisation step paying the
  sleep again. This does not measure a call that never returns: Guard cannot
  see one by construction, and what ends it is `-fuzztime` or the job's
  `timeout-minutes`, which no row here exercises.
- **R4a and R4b** break a property without a panic. R4a is reported at the
  seed pass, before the engine writes anything, which shows the exhaustion
  property is checked, not that mutation reaches it. R4b's mutation is
  chosen so that an exhausted stream still reads `Int` as 0; the first version
  of this row (`n := 2 + s.Int(maxLen)`) was reported by the exhaustion
  property instead, which is why the row names the property that fired.

## Limits

- Every time above is one run on one machine. The R2 and R3 times depend on
  the engine's random mutation order and on the host; a GitHub runner is
  slower. What would falsify the table is a re-run in which R2 or R3 reports
  SURVIVED at the 5 m budget.
- The rows run against `HEAD`, not the working tree; uncommitted edits to
  `internal/fuzzkit` are not in the copy, and the driver says so when there
  are any.
- A defect only a determinism check would see is not planted here: the
  determinism property is asserted by FuzzStream, but no row mutates `Stream`
  into keeping state across instances.
